# 加密备份：用密码保护导出的文件

状态：设计已确认（2026-11-22），按第 4 节的做法 A 实施；已实施（2026-11-22）。

## 1. 问题

现在的两种导出都是明文：

- `.secrets` 备份文件（二进制 plist，0.1.x 和 0.2.x 都能导入）；
- otpauth URL 列表（`.txt`，给别的验证器用）。

导出前只有一个警告框，提醒文件里是未加密的全部密钥。用户真正想要的往往只是「留一份备份」，可这份备份一旦放进网盘、发到另一台电脑，或者被同步工具带走，拿到文件的人就能生成所有验证码。`.secrets` 还会丢掉账号的排列顺序（它是一个按名称存的字典）。

## 2. 目标

- 导出时可以选「加密备份」：输入两次密码，得到一个只有用密码才能打开的文件。
- 导入时自动识别这种文件，要求输入密码；密码错误或者文件被改过，都明确提示，不导入任何内容。
- 加密备份保留账号的名称、otpauth URL 和顺序。
- 只用系统自带的框架（CryptoKit、CommonCrypto），不引入第三方库。

不做的事：

- 不和其他验证器互通。加密备份只给 GoldenPassport 自己恢复用；迁到别的 App 仍然用 otpauth URL 列表。
- 不去掉两种明文导出。otpauth URL 列表是迁到别的 App 的唯一办法，`.secrets` 是回退到 0.1.x 时要用的（README 的回退说明依赖它）。
- 不记住密码，不存进钥匙串，也不做自动定期备份。
- 不改数据格式：账号仍然存在登录钥匙串里，`compat.json` 不变。

绝不能出现的情况：

- 密码错误或文件损坏时，导入一堆乱码账号。
- 加密文件里留下明文的账号名称或密钥。
- 为了加密而在磁盘上留下明文的临时文件。

## 3. 用户看到的流程

导出：

1. 菜单「导出」的第一项是「加密备份（.gpbackup）…」，快捷键 ⌘E 从 `.secrets` 移到这一项。
2. 弹出密码窗口：「密码」和「再次输入密码」两个输入框，说明「忘记密码就无法恢复这份备份，GoldenPassport 不保存密码」。密码至少 8 个字符，两次一致才能继续，不要求字母、数字组合。
3. 选择保存位置，默认文件名 `GoldenPassport.gpbackup`，文件权限 `0600`。
4. 加密在后台进行（约零点几秒），完成后不弹窗；失败时提示原因。

导入：

1. 「导入…」的选择框多接受 `.gpbackup` 文件，说明文字随之更新。
2. 选中加密备份后弹出密码窗口（一个输入框）。
3. 密码错误或文件被改过：提示「密码不对，或者文件已损坏」，可以重新输入或取消。文件由更新版本的 GoldenPassport 创建（格式版本更高）：提示先升级。
4. 解密成功后，按现有规则导入：名称已存在的跳过，最后报告导入了多少条、跳过了多少条。

## 4. 做法

### 做法 A：自定义格式，PBKDF2 + AES-256-GCM（采用）

- 用 PBKDF2-HMAC-SHA256 从密码派生 256 位密钥，迭代 600,000 次（OWASP 当前对 PBKDF2-HMAC-SHA256 的建议值），随机盐 16 字节。CommonCrypto 的 `CCKeyDerivationPBKDF` 提供。
- 用 AES-256-GCM 加密，随机 nonce 12 字节。CryptoKit 的 `AES.GCM` 提供。GCM 自带认证标签：密码错误、密文或文件头被改过，解密都会失败，不会产生乱码。
- 盐、迭代次数和 nonce 写在文件头里，以后提高迭代次数不影响读旧文件。

### 做法 B：兼容 Aegis 的加密格式（不采用）

Aegis 用 scrypt 派生密钥。系统框架里没有 scrypt，要自己实现一个密码学原语，出错的风险比互通带来的好处大。

### 做法 C：加密磁盘映像（不采用）

用 `hdiutil` 生成带密码的 `.dmg`，Finder 里就能打开，不需要自己写加密。但导入要挂载卷、处理挂载点，又慢又容易留下残留；文件也比几 KB 的数据大得多。

### 为什么不用 Argon2 或 scrypt

它们更能抵抗显卡暴力破解，但系统框架都不提供。PBKDF2 加上足够长的密码对这个场景够用；文件头记录了算法名，将来要换算法时可以升级格式版本。

## 5. 文件格式（版本 1）

UTF-8 编码的 JSON，扩展名 `.gpbackup`：

```json
{
  "format": "GoldenPassport encrypted backup",
  "version": 1,
  "kdf": { "name": "PBKDF2-HMAC-SHA256", "iterations": 600000, "salt": "<base64，16 字节>" },
  "cipher": { "name": "AES-256-GCM", "nonce": "<base64，12 字节>" },
  "ciphertext": "<base64：密文 + 16 字节认证标签>"
}
```

- **编码**：二进制字段都用标准 base64（带 `=` 填充）。
- **附加认证数据（AAD）**：`format`、`version`、`kdf.name`、`kdf.iterations`、`kdf.salt`、`cipher.name` 用换行连接后的 UTF-8 字节。这样文件头里的参数被改过，解密同样失败。
- **明文**：UTF-8 JSON `{"version": 1, "accounts": [{"name": "…", "url": "otpauth://…"}, …]}`，按菜单顺序排列。
- **密码**：先做 Unicode NFC 规范化，再取 UTF-8 字节，避免同一个密码因输入法不同而得到不同的字节。

读取时的检查，任何一项不通过都不尝试解密：

- `format` 必须是上面的字符串；`version` 大于 1 时提示「由更新版本创建」。
- `kdf.name`、`cipher.name` 必须是上面的值。
- 迭代次数在 100,000～10,000,000 之间（防止被篡改的文件用极大的次数让 App 卡死）。
- 盐至少 16 字节，nonce 正好 12 字节，密文至少 16 字节（认证标签）。

解密后：明文必须是上面的 JSON，`accounts` 里每个 URL 都要能被现有的 otpauth 解析器读懂；有读不懂的条目，按 otpauth URL 列表导入时的做法报告并跳过。

## 6. 代码位置

- Core：`EncryptedBackup`（`seal(accounts:password:)` → `Data`，`open(_:password:)` → `[Account]`，错误类型 `EncryptedBackupError`），PBKDF2 和 AES-GCM 都在这里，可以完整地单元测试。
- App：`StatusMenuController` 的导出菜单和导入流程；`PasswordPrompt` 用带密码输入框的提示框（`NSAlert`）询问密码，和现有导入导出的流程一样是模态的。
- 界面文字的中英文翻译、README（菜单表、安全与隐私）、CHANGELOG。

## 7. 测试

- PBKDF2-HMAC-SHA256 用 RFC 7914 第 11 节的测试向量核对。
- 加密后解密得到同样的账号和顺序；同一份数据加密两次，盐和 nonce 不同，密文也不同。
- 密码错误、密文改一个字节、文件头参数（迭代次数、盐）改动、截断的文件，都失败且报同一个「密码不对或文件已损坏」错误。
- 格式版本 2、未知算法名、迭代次数越界、盐或 nonce 长度不对，各自报对应的错误，并且不做密钥派生。
- 加密文件里搜不到账号名称和密钥的明文。
- NFC 和 NFD 两种写法的同一个密码能互相解开。
