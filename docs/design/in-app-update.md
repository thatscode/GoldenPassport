# 应用内更新：下载、校验、替换、重启

状态：设计已确认（2026-11-21），按第 4 节的做法 A 实施。第 7 节「不同用户的环境」是确认时按"App 面向所有公网用户"的要求补充的。

## 1. 问题

「检查更新」发现新版本后，弹窗只有「查看发布页面」和「稍后」。用户要自己打开 GitHub、下载 zip、解压，再到终端里运行 `install.sh`。别的软件点一下就能升级，GoldenPassport 却要走五六步。

当初只给发布页面，是有意这么做的（`StatusMenuController.presentUpdate` 的注释：安装要走 `install.sh`，它会先备份），主要是担心 0.1.x → 0.2 的数据迁移出问题。现在情况变了：0.2.x 的账号都存在登录钥匙串里，数据格式都是 2。从一个 0.2.x 升到另一个 0.2.x 不迁移任何数据，只是把 App 换掉。

## 2. 目标

- 发现新版本时，弹窗里多一个「下载并安装」按钮。点一下以后，App 自己下载、校验、替换，然后重新打开新版本，全程不用开终端。
- 只要有一项校验没通过，就不做任何改动：旧版本照常运行，并说明原因。
- 新版本如果会改动数据格式、要求先升级到某个中间版本，或者兼容性不明，就不允许在 App 里安装：照旧显示提示，只给「查看发布页面」。
- 不同用户的环境（系统版本、芯片、安装位置、账号权限、网络、安全软件）都要有明确的处理，见第 7 节。

不做的事：

- 不在后台悄悄安装。自动检查仍然只在菜单顶部显示「新版本 x 可用…」，要用户点了「下载并安装」才会动手。
- 不弹管理员密码框。当前账号改不了 App 所在的位置时，退回发布页面，并说明原因。
- 不做增量更新，每次都下载完整的 zip（约 3 MB）。
- 不替代 `install.sh`。第一次装、跨数据格式升级，以及回退，仍然用脚本。

绝不能出现的情况：

- 装上一个不是我们签名的 App。
- 换到一半失败，结果新旧两个版本都没了，或者两份同时在运行。
- 为了更新而多留一份明文密钥，比如像 `install.sh` 那样把数据目录复制一份当备份。

## 3. 什么时候可以在 App 里直接安装

下面的条件全部满足，才显示「下载并安装」：

| 方面 | 条件 | 不满足时 |
|---|---|---|
| 发布 | `compat.json` 读得到，而且 `UpdateChecker` 没有给出任何提示（没有 `dataFormatChange`、`upgradeFirst`、`compatibilityUnknown`） | 照旧显示现有的警告文字，并加一句：「这个版本不能在 App 里直接安装，请用安装包里的 install.sh 安装，它会先备份。」 |
| 发布 | Release 里有名为 `GoldenPassport-<版本>.zip` 的附件 | 只给发布页面 |
| 运行中的 App | 自己带 Developer ID 签名，有 Team ID（自己打的 ad hoc 包和 Dev 版没有） | 只给发布页面：「这一份不是正式发布的版本，不能自动更新。」 |
| 运行中的 App | 没有被系统隔离运行（路径里没有 `/AppTranslocation/`，比如直接从「下载」文件夹打开的那份） | 「GoldenPassport 现在的位置不能直接替换。请把它移到「应用程序」文件夹，或者用安装包里的 install.sh 安装。」 |
| 运行中的 App | 当前账号能写 App 所在的文件夹，也能写 App 本身 | 「当前账号不能修改 \<路径\>，请用管理员账号运行 install.sh。」 |

## 4. 考虑过的做法

| 做法 | 结论 | 原因 |
|---|---|---|
| A. 自己写一个小的更新器 | **采用**（2026-11-21 选定） | 不引入第三方代码，这对存着 MFA 密钥的 App 很重要。信任只靠 Apple 签名，不用多保管一把私钥。发布流程和 zip 不变，能不能升级仍然只看 `compat.json` 一套规则。代价是边界情况都要自己处理，预计 400–600 行代码，另加测试。 |
| B. Sparkle | 不采用 | 要嵌入一个带 XPC 辅助进程的框架，在纯 SwiftPM 的打包里手动签名、公证。要多保管一把 EdDSA 私钥，每次发布还要生成并托管 appcast。`compat.json` 的规则得在 appcast 里再写一遍，界面也会换成 Sparkle 自己的。 |
| C. 下载后运行包里的 `install.sh` | 不采用 | zip 里的脚本没有签名，谁能改 Release 附件，谁就能在用户机器上执行任意命令。另外每次升级都会多出一份未加密的备份。 |

## 5. 方案

### 5.1 界面

可以安装时的弹窗：

```
GoldenPassport 0.2.4 已发布
你现在使用的是 0.2.3。

        [下载并安装]  [查看发布页面]  [稍后]
```

点「下载并安装」后，出现一个小窗口：

```
正在更新 GoldenPassport
正在下载 0.2.4…  ███████░░░  1.9 / 3.0 MB
                                   [取消]
```

接着依次显示「正在校验…」「正在核对数据（可能会请求访问钥匙串）…」「正在安装…」。只有下载阶段可以取消。安装完成后旧版本退出，新版本自动打开，并弹一次：

```
已更新到 GoldenPassport 0.2.4
              [查看更新内容]  [好]
```

失败时显示「更新没有完成」、原因，以及「GoldenPassport 没有做任何改动，你仍在使用 0.2.3。」，按钮为「查看发布页面」和「好」。网络原因失败时，额外说明可以在发布页面用浏览器下载，再运行 `install.sh` 安装。

菜单顶部的「新版本 x 可用…」打开的是同一个弹窗。更新进行中，「检查更新…」和这一项都暂时不可用。

### 5.2 下载

- 地址用 GitHub API 返回的附件 `browser_download_url`。GitHub 会把它重定向到 `*.githubusercontent.com`，跟随重定向即可。请求的身份和检查更新一样，只带 `User-Agent: GoldenPassport/<版本>`。
- 跟随系统的代理设置，包括 PAC 自动配置。会话配置不能单独设置代理，`.ephemeral` 默认就会用系统代理。
- 用带进度的下载任务。超时不能沿用检查更新的 30 秒：连续 60 秒收不到数据，或者 10 分钟还没下完，就算失败。国内访问 GitHub 附件经常很慢，3 MB 在 10 分钟内应该够用；不够用户也可以随时取消。
- 下载到 `~/Library/Caches/<bundle id>/Updates/<版本>/`，目录权限 `0700`。每次开始更新前、失败后、新版本启动后，都把整个 `Updates` 目录删掉。
- 文件大小必须等于 API 返回的 `size`。API 的附件信息里有 `digest`（如 `sha256:b83ef521…`，2026-11-21 在 v0.2.2 上确认过），有就必须一致；没有也照常继续，因为真正的信任依据是 5.3 的签名校验。公共 Wi-Fi 的登录页之类返回的错误内容，会在这一步或解压时被发现。
- 用 `/usr/bin/ditto -x -k` 解压。解出来必须正好有一个 `GoldenPassport.app`，在 `GoldenPassport-<版本>/` 下面，否则算失败。
- URLSession 下载的文件不带隔离属性，我们也不加，所以系统不会再做首次打开检查。这一步由 5.3 的公证校验代替。

### 5.3 校验

校验的是 5.4 第 1 步复制到目标文件夹旁边的那一份，保证校验过的就是将要运行的那一份。

1. **签名**：用 `SecStaticCodeCheckValidity` 校验，参数为 `kSecCSStrictValidate | kSecCSCheckAllArchitectures | kSecCSCheckNestedCode`，要求为：

   ```
   anchor apple generic
   and identifier "<运行中 App 的 bundle id>"
   and certificate leaf[subject.OU] = "<运行中 App 的 Team ID>"
   and certificate 1[field.1.2.840.113635.100.6.2.6]
   and certificate leaf[field.1.2.840.113635.100.6.1.13]
   and notarized
   ```

   Team ID 从运行中 App 自己的签名里读（`SecCodeCopySelf` + `SecCodeCopySigningInformation` 的 `kSecCodeInfoTeamIdentifier`），代码里不写死。两个 OID 分别对应 Developer ID 中间证书和 Developer ID Application 证书。`notarized` 要求带公证票据，我们发布的 zip 都已装订票据。
2. **Info.plist**：`CFBundleIdentifier` 和运行中的一致；版本（`CFBundleShortVersionString` 加 `GPPrerelease`）正好等于这次要装的版本；`GPDataDirectoryName` 和 `GPKeychainService` 都和运行中的一致，保证新旧版本用同一份数据；`LSMinimumSystemVersion` 不高于当前系统，否则说明「这个版本需要 macOS X 或更高版本」；可执行文件包含当前 Mac 的架构。
3. **版本**：必须比运行中的新，不允许降级。

信任靠的是第 1 条。第 2 条防的是我们自己发错包，比如误传了 Dev 版。

### 5.4 替换和重启

下面用 T 表示运行中 App 的位置（`Bundle.main.bundleURL`，先解析符号链接），P 表示 T 所在的文件夹。第 1–6 步都在旧版本仍在运行时完成，任何一步失败都由旧版本恢复原状并报错。

所有子进程（`ditto`、新版本的数据检查）都用参数数组启动，不经过 shell，这样路径里有空格或中文也没问题。整个过程只新建一个 App 包，再改名替换，从不改动已有 App 包里的文件。

| 步骤 | 做什么 | 失败时 |
|---|---|---|
| 1 | 用 `ditto` 把解压出的 App 复制到 `P/.GoldenPassport.app.updating`（同一个卷，后面改名是原子操作；名字不以 `.app` 结尾，Launch Services 不会把它当成 App）。目标已存在就先删掉 | 删掉临时副本，报错 |
| 2 | 按 5.3 校验这份副本 | 同上 |
| 3 | 数据检查：运行副本里的 `GoldenPassport --migrate-data`（默认数据目录），最多等 2 分钟。要求退出码为 0，`status` 为 `already-migrated` 或 `no-data`。这一步会读钥匙串：Team ID 相同、之前点过「始终允许」的用户不会看到授权框（D3 第 6 步验证过）；钥匙串被锁、或之前只点了「允许」的用户会看到系统授权框，所以要留出 2 分钟。这也是新版本第一次在这台 Mac 上执行，被安全软件拦下的话，在这里就会失败 | 同上，并附上检查输出里的状态（只有名称，没有密钥） |
| 4 | 把 T 移到废纸篓（`FileManager.trashItem`），记下它在废纸篓里的位置 R。外置磁盘用这块磁盘自己的废纸篓 | 删掉临时副本，报错。有些网络卷没有废纸篓，会在这一步失败，不做任何改动 |
| 5 | 把临时副本改名为 T | 把 R 移回 T，删掉临时副本，报错 |
| 6 | 用 `NSWorkspace.openApplication` 打开 T，`createsNewApplicationInstance = true`，参数 `--after-update <旧进程 pid> --updated-from <旧版本>` | 把新版本移到废纸篓，把 R 移回 T，报错 |
| 7 | 旧版本正常退出（`NSApp.terminate`，照常关掉 HTTP 服务和快捷键） | — |

旧版本留在废纸篓里，想退回去的话可以拖回来；数据格式没变，旧版本能直接读。

账号的改动本来就是立即保存的。但如果「管理账号」等窗口里有正在输入、还没保存的内容，退出时会丢失，所以第 4 步之前要先处理（见第 11 节）。

### 5.5 新版本启动时

- 带 `--after-update <pid>` 启动时，先最多等 10 秒，等那个进程退出，然后才做「只运行一份」的检查。10 秒后旧进程还在，就按现有逻辑处理（提示已经在运行，然后退出）。
- 删掉 `Updates` 缓存目录。
- 带 `--updated-from` 时，弹一次 5.1 里的「已更新到 …」，「查看更新内容」打开这个版本的发布页面。如果用户打开了快捷键自动填入，但辅助功能授权不在了（`AXIsProcessTrusted()` 为 false），弹窗里再加一句说明，并给一个「打开辅助功能设置」按钮。C3 在 macOS 27.2 上验证过，授权会保留；这个提示仍然保留，以防在别的系统版本上丢失。
- 菜单栏图标的位置、语言、设置都存在同一个 bundle id 的 defaults 里，换 App 不受影响。「登录时打开」用的是 `SMAppService.mainApp`，认的是 bundle id 和路径，路径没变，应该保持（要在端到端测试中确认）。

### 5.6 代码结构

- **GoldenPassportCore**（可以单元测试）：
  - 判断能不能在 App 里安装：输入是 `AvailableUpdate` 和运行中 App 的状态（有没有 Team ID、是否被隔离运行、能不能写），输出是「可以安装」或「只给发布页面」加原因。
  - `UpdateChecker` 多返回 zip 附件的地址、大小和 digest。
  - 校验 Info.plist 的纯函数；拼签名要求字符串的函数（bundle id 和 Team ID 里的引号要转义）。
  - 安装步骤（5.4）写成状态机，文件操作、运行数据检查、打开 App 都通过协议注入，这样每个失败点都能测到。
  - 解析 `--after-update` 和 `--updated-from`。
- **GoldenPassport**（界面）：弹窗、进度窗口、真正调用 Security 框架做签名校验、在 `main()` 里处理 `--after-update`、新增的中英文字符串。

## 6. 安全

- 信任依据是 Apple：新版本必须是运行中 App 同一个 Team 的 Developer ID 签名，并且已经公证。只拿到 GitHub 账号推不了恶意更新，因为还需要 Developer ID 私钥。HTTPS 只负责传输，不是信任依据；即使公司代理解密了 HTTPS 流量，也换不了包。
- 信任的是整个 Team ID，而不是我们手上那一张证书。这样证书 2027-12-19 到期续签后，更新还能继续用。代价是：这个 Team 的账号持有人（朋友）自己签的包也会被接受。这和用户今天手动安装时信任的范围一样。
- 如果将来换了 Team ID（比如改用自己的开发者账号），新版本会被签名校验拒绝，用户要手动装一次，同时重新授权钥匙串和辅助功能。这是有意的：Team ID 一变，系统本来就会把它当成另一个开发者。
- 只升不降，防止被回滚到有漏洞的旧版本。
- 不复制数据目录，不产生新的明文副本。
- 网络请求和检查更新一样，只透露 App 版本号。只有用户点了「下载并安装」才会下载。
- 端到端测试用的环境变量（第 9 节）发布版里也有。它只能被已经能以用户身份运行程序的人利用，而且签名校验和只升不降照样生效，所以没法用它装上别人的包。

## 7. 不同用户的环境

| 环境 | 会发生什么 | 怎么处理 |
|---|---|---|
| macOS 13 到最新版 | 用到的接口（`NSWorkspace.openApplication`、`createsNewApplicationInstance`、`FileManager.trashItem`、`SecStaticCode`）在 macOS 13 之前就有了 | 最低部署版本是 13，编译器会检查接口是否可用；CI 的 macOS 15 + Xcode 16.0 任务也会编译。`notarized` 这个要求在 13 上是否可用，由实现者确认 |
| 将来的版本要求更高的 macOS | 下载后的 Info.plist 校验发现 `LSMinimumSystemVersion` 高于当前系统 | 不安装，说明需要的系统版本。以后可以在 `compat.json` 里加一个可选字段提前判断（旧版本会忽略不认识的字段），这次不做 |
| Intel 和 Apple 芯片 | 发布包是通用二进制 | 校验时确认包里有当前 Mac 的架构 |
| 装在 `/Applications`、`~/Applications`、其他文件夹或外置磁盘 | 原地替换；用户改过的 App 名字保留 | 外置磁盘用它自己的废纸篓；没有废纸篓的卷（部分网络卷）在第 4 步失败，不做改动 |
| 直接从「下载」文件夹打开（被隔离运行），或者从只读位置运行 | 不能原地替换 | 不显示安装按钮，提示把 App 移到「应用程序」文件夹 |
| 标准账号（不是管理员），或者 App 是另一个账号装的 | 写不了 App 所在的位置 | 不显示安装按钮，说明原因，指向 `install.sh` |
| 一台 Mac 上多个用户同时在运行 | 只有能写 App 的那个用户能更新；另一个用户正在运行的那一份不受影响，直到它退出 | 另一个用户下次打开时就是新版本。「只运行一份」的检查只看当前用户自己的进程，和现在一样 |
| macOS 13 起的「App 管理」保护 | 系统会拦截 App 修改别的开发者的 App | 我们只新建包、改名，不改动已有包里的文件，而且新旧版本 Team ID 相同。端到端测试确认没有弹出「App 管理」授权 |
| 公司电脑上的安全软件（如按签名放行的白名单工具） | 可能不允许新版本执行 | 第 3 步是新版本第一次执行，被拦下就在替换前失败，旧版本不受影响 |
| 网络：国内访问 GitHub 慢或断断续续、系统代理或 PAC、需要认证的公司代理、公共 Wi-Fi 登录页 | 下载慢、失败，或者拿到的内容不对 | 跟随系统代理；60 秒收不到数据或 10 分钟没下完算失败；可以取消；内容不对会在大小、digest 或解压时发现。失败弹窗给出「查看发布页面」，用户可以用浏览器下载（浏览器可能已经通过代理认证） |
| GitHub API 限流（公司共用一个出口 IP） | 检查更新本身就会报错（现有逻辑） | 不变；下载附件不受同样的限制 |
| 系统时间不准 | HTTPS 连接失败 | 按下载失败处理。签名校验看的是签名时的时间戳，不受影响 |
| 钥匙串被锁，或者当初只点了「允许」而不是「始终允许」 | 第 3 步会弹出系统授权框 | 进度窗口提示可能会请求访问钥匙串；等 2 分钟，拒绝或超时就不做改动 |
| 升级后辅助功能授权丢失（C3 在 macOS 27.2 上没有发生） | 快捷键只能复制验证码，不能自动填入 | 「已更新」弹窗里提示，并给「打开辅助功能设置」按钮 |
| 「登录时打开」、菜单栏图标位置、语言 | 绑定的是 bundle id 和路径，都没变 | 端到端测试确认 |
| 磁盘空间不足 | 某一步写不进去 | 恢复原状并提示 |
| 路径里有空格或中文 | — | 子进程都用参数数组启动，不经过 shell |
| 内测版、自己打的 ad hoc 包、Dev 版 | 没有 Team ID，或者数据格式不同 | 不显示安装按钮（第 3 节） |
| 0.2.2 及更早的版本 | 没有这个功能 | 要手动装一次（第 8 节） |
| 以后通过 Homebrew 安装（C5） | brew 和 App 都会去更新 App | cask 里写 `auto_updates true`，让 brew 知道 App 会自己更新。brew 装到 `/Applications` 的 App 归当前用户所有，可以原地更新 |
| 系统语言不是中文或英文 | — | 新增文案都有中英文，其他语言和现在一样显示英文 |

## 8. 第一次上线

## 9. 测试

单元测试（Core，CI 上跑）：

- 第 3 节的判断：各种提示和运行状态组合，分别得到「可以安装」或「只给发布页面」加对应原因。
- 附件选择：只认 `GoldenPassport-<版本>.zip`；能解析 `sha256:` 前缀的 digest；没有 digest 时照常继续。
- Info.plist 校验：版本、bundle id、数据目录名、钥匙串服务名不一致，系统版本不够，或者缺当前架构，都要拒绝。

- `--after-update` 的参数解析和缓存目录清理。

端到端测试（发布前在本机，用 Developer ID 签名并公证的包）：

- 用探针版本：独立的 bundle id、数据目录和钥匙串服务名，参考 D3 第 6 步的做法，**绝不碰真实的钥匙串条目和数据目录**。放在临时文件夹里运行，用一个仅供测试的环境变量把「最新版本」地址指向本机服务器。

## 12. 决定（2026-11-21 确认）

1. 只在点了「下载并安装」后才执行，不在后台静默安装。
2. `compat.json` 缺失或读不懂（兼容性不明）也算不允许，只给发布页面。
3. 旧版本移到废纸篓，不在 `~/GoldenPassport-backups` 里做备份（数据没动，也避免多一份明文）。
4. 信任整个 Team ID，而不是只认一张证书（第 6 节）。
5. 更新成功后，新版本弹一次「已更新到 …」。
6. 没有写入权限或位置不对时，不弹管理员密码框，退回发布页面并说明原因。

## 13. 实施记录

2026-11-21 实现完成。第 3 节的判断、5.2 下载、5.3 校验、5.4 替换都在 Core（`UpdateEligibility`、`UpdateDownloader`、`UpdatePackageCheck`、`UpdateInstaller`），App 里的 `UpdateController` 负责界面和启动新版本。共 182 个测试通过。

和第 5 节的差别：

- 下载用 data task、自己写文件，这样「卡住」的判断能看到每一块实际收到的数据。
- 进度窗口浮在其他 App 之上，App 失去焦点时也不隐藏。否则窗口被系统收起，看不到进度和「取消」。
- 新版本先完成启动，再在运行循环里等旧版本退出（5.5）。旧版本要等系统报告新版本已经启动才会退出，如果新版本在启动前就阻塞等待，每次更新都会多卡 10 秒。

端到端测试（macOS 27.2.1，Developer ID 签名并公证的探针版本，路径里有空格和中文）：

- 正常升级：点「下载并安装」后约 0.8 秒旧版本退出，约 1 秒弹出「已更新」。新版本经过公证，没有残留临时副本和下载缓存，钥匙串没有弹框，「登录时打开」保持开启。
- 服务器返回 HTML、ad hoc 签名的包、版本号不符、下载卡住（约 60 秒超时）、下载中取消、下载期间打开了添加账号窗口、目标文件夹只读：都按设计提示，没有做任何改动。限速下载（约 21 秒）正常装上。
- C3：同一签名原地升级后，辅助功能授权保留。「已更新」提示里的授权提醒仍然保留，以防在别的系统版本上丢失。
- 没有测：从被隔离的位置运行（要在 Gatekeeper 的确认框里手动确认，只有单元测试）；断网和 zip 损坏（摘要不符由单元测试覆盖）；macOS 13 / 14（没有可用的环境）。
- 第 9 节最后一项（2026-11-22）：发布 0.3.0 后，在维护者自己的 Mac（macOS 27.2.1）上从 0.3.0-rc.1 点「下载并安装」升级到 0.3.0，成功。装好的是 0.3.0（build 170），经过公证；只有一个进程在运行；没有残留暂存目录和下载缓存。

以后可以改进：`compat.json` 是唯一能拦住改变数据格式的版本的地方，第 3 步的 `--migrate-data` 在核对失败之前会真的迁移数据。可以加一个只读的检查参数，让第 3 步只核对、不迁移。
