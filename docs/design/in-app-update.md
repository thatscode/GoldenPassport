# 应用内更新：下载、校验、替换、重启

状态：设计稿（2026-11-21），等确认。

## 1. 问题

「检查更新」发现新版本后，弹窗只有「查看发布页面」和「稍后」。用户要自己打开 GitHub、下载 zip、解压，再到终端里运行 `install.sh`。别的软件点一下就能升级，GoldenPassport 却要走五六步。

当初只给发布页面，是有意这么做的（`StatusMenuController.presentUpdate` 的注释：安装要走 `install.sh`，它会先备份），主要是担心 0.1.x → 0.2 的数据迁移出问题。现在情况变了：0.2.x 的账号都存在登录钥匙串里，数据格式都是 2。从一个 0.2.x 升到另一个 0.2.x 不迁移任何数据，只是把 App 换掉。

## 2. 目标

- 发现新版本时，弹窗里多一个「下载并安装」按钮。点一下以后，App 自己下载、校验、替换，然后重新打开新版本，全程不用开终端。
- 只要有一项校验没通过，就不做任何改动：旧版本照常运行，并说明原因。
- 新版本如果会改动数据格式、要求先升级到某个中间版本，或者兼容性不明，就不允许在 App 里安装：照旧显示提示，只给「查看发布页面」。

不做的事：

- 不在后台悄悄安装。自动检查仍然只在菜单顶部显示「新版本 x 可用…」，要用户点了「下载并安装」才会动手。
- 不弹管理员密码框。当前账号改不了 App 所在的位置时，退回发布页面，并说明原因。
- 不做增量更新，每次都下载完整的 zip（约 3 MB）。
- 不替代 `install.sh`。第一次装、跨数据格式升级，以及回退，仍然用脚本。

绝不能出现的情况：

- 装上一个不是我们签名的 App。
- 换到一半失败，结果新旧两个版本都没了，或者两份同时在运行。
- 为了更新而多留一份明文密钥，比如像 `install.sh` 那样把数据目录复制一份当备份。

## 3. 什么时候可以在 App 里直接安装

下面的条件全部满足，才显示「下载并安装」：

| 方面 | 条件 | 不满足时 |
|---|---|---|
| 发布 | `compat.json` 读得到，而且 `UpdateChecker` 没有给出任何提示（没有 `dataFormatChange`、`upgradeFirst`、`compatibilityUnknown`） | 照旧显示现有的警告文字，并加一句：「这个版本不能在 App 里直接安装，请用安装包里的 install.sh 安装，它会先备份。」 |
| 发布 | Release 里有名为 `GoldenPassport-<版本>.zip` 的附件 | 只给发布页面 |
| 运行中的 App | 自己带 Developer ID 签名，有 Team ID（自己打的 ad hoc 包和 Dev 版没有） | 只给发布页面：「这一份不是正式发布的版本，不能自动更新。」 |
| 运行中的 App | 没有被系统隔离运行（路径里没有 `/AppTranslocation/`，比如直接从「下载」文件夹打开的那份） | 「GoldenPassport 现在的位置不能直接替换。请把它移到「应用程序」文件夹，或者用安装包里的 install.sh 安装。」 |
| 运行中的 App | 当前账号能写 App 所在的文件夹，也能写 App 本身 | 「当前账号不能修改 \<路径\>，请用管理员账号运行 install.sh。」 |

## 4. 考虑过的做法

| 做法 | 结论 | 原因 |
|---|---|---|
| A. 自己写一个小的更新器 | **采用**（2026-11-21 选定） | 不引入第三方代码，这对存着 MFA 密钥的 App 很重要。信任只靠 Apple 签名，不用多保管一把私钥。发布流程和 zip 不变，能不能升级仍然只看 `compat.json` 一套规则。代价是边界情况都要自己处理，预计 400–600 行代码，另加测试。 |
| B. Sparkle | 不采用 | 要嵌入一个带 XPC 辅助进程的框架，在纯 SwiftPM 的打包里手动签名、公证。要多保管一把 EdDSA 私钥，每次发布还要生成并托管 appcast。`compat.json` 的规则得在 appcast 里再写一遍，界面也会换成 Sparkle 自己的。 |
| C. 下载后运行包里的 `install.sh` | 不采用 | zip 里的脚本没有签名，谁能改 Release 附件，谁就能在用户机器上执行任意命令。另外每次升级都会多出一份未加密的备份。 |

## 5. 方案

### 5.1 界面

可以安装时的弹窗：

```
GoldenPassport 0.2.4 已发布
你现在使用的是 0.2.3。

        [下载并安装]  [查看发布页面]  [稍后]
```

点「下载并安装」后，出现一个小窗口：

```
正在更新 GoldenPassport
正在下载 0.2.4…  ███████░░░  1.9 / 3.0 MB
                                   [取消]
```

接着依次显示「正在校验…」「正在安装…」。只有下载阶段可以取消。安装完成后旧版本退出，新版本自动打开，并弹一次：

```
已更新到 GoldenPassport 0.2.4
              [查看更新内容]  [好]
```

失败时显示「更新没有完成」、原因，以及「GoldenPassport 没有做任何改动，你仍在使用 0.2.3。」，按钮为「查看发布页面」和「好」。

菜单顶部的「新版本 x 可用…」打开的是同一个弹窗。更新进行中，「检查更新…」和这一项都暂时不可用。

### 5.2 下载

- 地址用 GitHub API 返回的附件 `browser_download_url`，请求的身份和检查更新一样，只带 `User-Agent: GoldenPassport/<版本>`。用带进度的下载任务；整个下载的超时不能沿用检查更新的 30 秒，要放宽到几分钟。
- 下载到 `~/Library/Caches/<bundle id>/Updates/<版本>/`，目录权限 `0700`。每次开始更新前、失败后、新版本启动后，都把整个 `Updates` 目录删掉。
- 文件大小必须等于 API 返回的 `size`。API 的附件信息里有 `digest`（如 `sha256:b83ef521…`，2026-11-21 在 v0.2.2 上确认过），有就必须一致；没有也照常继续，因为真正的信任依据是 5.3 的签名校验。
- 用 `/usr/bin/ditto -x -k` 解压。解出来必须正好有一个 `GoldenPassport.app`，在 `GoldenPassport-<版本>/` 下面，否则算失败。
- URLSession 下载的文件不带隔离属性，我们也不加，所以系统不会再做首次打开检查。这一步由 5.3 的公证校验代替。

### 5.3 校验

校验的是 5.4 第 1 步复制到目标文件夹旁边的那一份，保证校验过的就是将要运行的那一份。

1. **签名**：用 `SecStaticCodeCheckValidity` 校验，参数为 `kSecCSStrictValidate | kSecCSCheckAllArchitectures | kSecCSCheckNestedCode`，要求为：

   ```
   anchor apple generic
   and identifier "<运行中 App 的 bundle id>"
   and certificate leaf[subject.OU] = "<运行中 App 的 Team ID>"
   and certificate 1[field.1.2.840.113635.100.6.2.6]
   and certificate leaf[field.1.2.840.113635.100.6.1.13]
   and notarized
   ```

   Team ID 从运行中 App 自己的签名里读（`SecCodeCopySelf` + `SecCodeCopySigningInformation` 的 `kSecCodeInfoTeamIdentifier`），代码里不写死。两个 OID 分别对应 Developer ID 中间证书和 Developer ID Application 证书。`notarized` 要求带公证票据，我们发布的 zip 都已装订票据。
2. **Info.plist**：`CFBundleIdentifier` 和运行中的一致；版本（`CFBundleShortVersionString` 加 `GPPrerelease`）正好等于这次要装的版本；`GPDataDirectoryName` 和 `GPKeychainService` 都和运行中的一致，保证新旧版本用同一份数据；`LSMinimumSystemVersion` 不高于当前系统；可执行文件包含当前 Mac 的架构。
3. **版本**：必须比运行中的新，不允许降级。

信任靠的是第 1 条。第 2 条防的是我们自己发错包，比如误传了 Dev 版。

### 5.4 替换和重启

下面用 T 表示运行中 App 的位置（`Bundle.main.bundleURL`），P 表示 T 所在的文件夹。第 1–6 步都在旧版本仍在运行时完成，任何一步失败都由旧版本恢复原状并报错。

| 步骤 | 做什么 | 失败时 |
|---|---|---|
| 1 | 用 `ditto` 把解压出的 App 复制到 `P/.GoldenPassport.app.updating`（同一个卷，后面改名是原子操作；名字不以 `.app` 结尾，Launch Services 不会把它当成 App）。目标已存在就先删掉 | 删掉临时副本，报错 |
| 2 | 按 5.3 校验这份副本 | 同上 |
| 3 | 数据检查：运行副本里的 `GoldenPassport --migrate-data`（默认数据目录），最多等 60 秒。要求退出码为 0，`status` 为 `already-migrated` 或 `no-data`。这一步会读钥匙串；Team ID 相同，所以不会弹授权框（D3 第 6 步验证过） | 同上，并附上检查输出里的状态（只有名称，没有密钥） |
| 4 | 把 T 移到废纸篓（`FileManager.trashItem`），记下它在废纸篓里的位置 R | 删掉临时副本，报错 |
| 5 | 把临时副本改名为 T | 把 R 移回 T，删掉临时副本，报错 |
| 6 | 用 `NSWorkspace.openApplication` 打开 T，`createsNewApplicationInstance = true`，参数 `--after-update <旧进程 pid> --updated-from <旧版本>` | 把新版本移到废纸篓，把 R 移回 T，报错 |
| 7 | 旧版本正常退出（`NSApp.terminate`，照常关掉 HTTP 服务和快捷键） | — |

旧版本留在废纸篓里，想退回去的话可以拖回来；数据格式没变，旧版本能直接读。

账号的改动本来就是立即保存的。但如果「管理账号」等窗口里有正在输入、还没保存的内容，退出时会丢失，所以第 4 步之前要先处理（见第 10 节）。

### 5.5 新版本启动时

- 带 `--after-update <pid>` 启动时，先最多等 10 秒，等那个进程退出，然后才做「只运行一份」的检查。10 秒后旧进程还在，就按现有逻辑处理（提示已经在运行，然后退出）。
- 删掉 `Updates` 缓存目录。
- 带 `--updated-from` 时，弹一次 5.1 里的「已更新到 …」。「查看更新内容」打开这个版本的发布页面。
- 菜单栏图标的位置、语言、设置都存在同一个 bundle id 的 defaults 里，换 App 不受影响。「登录时打开」认的是 bundle id 和路径，路径没变，应该保持（要在测试中确认）。

### 5.6 代码结构

- **GoldenPassportCore**（可以单元测试）：
  - 判断能不能在 App 里安装：输入是 `AvailableUpdate` 和运行中 App 的状态（有没有 Team ID、是否被隔离运行、能不能写），输出是「可以安装」或「只给发布页面」加原因。
  - `UpdateChecker` 多返回 zip 附件的地址、大小和 digest。
  - 校验 Info.plist 的纯函数；拼签名要求字符串的函数（bundle id 和 Team ID 里的引号要转义）。
  - 安装步骤（5.4）写成状态机，文件操作、运行数据检查、打开 App 都通过协议注入，这样每个失败点都能测到。
  - 解析 `--after-update` 和 `--updated-from`。
- **GoldenPassport**（界面）：弹窗、进度窗口、真正调用 Security 框架做签名校验、在 `main()` 里处理 `--after-update`、新增的中英文字符串。

## 6. 安全

- 信任依据是 Apple：新版本必须是运行中 App 同一个 Team 的 Developer ID 签名，并且已经公证。只拿到 GitHub 账号推不了恶意更新，因为还需要 Developer ID 私钥。HTTPS 只负责传输，不是信任依据。
- 信任的是整个 Team ID，而不是我们手上那一张证书。这样证书 2027-12-19 到期续签后，更新还能继续用。代价是：这个 Team 的账号持有人（朋友）自己签的包也会被接受。这和用户今天手动安装时信任的范围一样。
- 只升不降，防止被回滚到有漏洞的旧版本。
- 不复制数据目录，不产生新的明文副本。
- 网络请求和检查更新一样，只透露 App 版本号。只有用户点了「下载并安装」才会下载。

## 7. 第一次上线

- 只有带这个功能的版本才会显示「下载并安装」。假设它在 0.2.3 里上线，0.2.2 及更早的用户这一次还得手动装 0.2.3（Release 说明要写清楚），从 0.2.3 → 0.2.4 开始才能一键升级。
- TODO 里的 C3（同一签名升级后辅助功能授权是否保留）在第 8 节的端到端测试里一并验证。结果决定 README 和安装说明里「升级后要重新授权」怎么改。

## 8. 测试

单元测试（Core，CI 上跑）：

- 第 3 节的判断：各种提示和运行状态组合，分别得到「可以安装」或「只给发布页面」加对应原因。
- 附件选择：只认 `GoldenPassport-<版本>.zip`；能解析 `sha256:` 前缀的 digest；没有 digest 时照常继续。
- Info.plist 校验：版本、bundle id、数据目录名、钥匙串服务名不一致，或缺当前架构，都要拒绝。
- 签名要求字符串的拼法和转义。
- 安装状态机：在第 1–6 步各注入一次失败，确认每次都恢复原状（T 还是旧版本，临时副本已删除，废纸篓里的东西已移回）。再用临时目录和假的 App 包、真实 `FileManager` 跑一遍完整流程。
- 签名校验会拒绝 ad hoc 签名的包。这一项可以在 CI 上用 `codesign -s -` 临时签一个测试包来测。
- `--after-update` 的参数解析和缓存目录清理。

端到端测试（发布前在本机，用 Developer ID 签名并公证的包）：

- 用探针版本：独立的 bundle id、数据目录和钥匙串服务名，参考 D3 第 6 步的做法，**绝不碰真实的钥匙串条目和数据目录**。放在临时文件夹里运行，用一个仅供测试的环境变量把「最新版本」地址指向本机服务器（签名校验照样生效，所以这个变量没法用来装别人的包）。
- 要覆盖的情况：正常升级；下载中取消；断网；zip 损坏；服务器给出 ad hoc 签名的包（必须拒绝）；版本号不符；从被隔离的位置运行；目标文件夹只读。
- 升级后要检查：钥匙串不弹窗；菜单栏图标位置不变；「登录时打开」仍然开着；**辅助功能授权是否保留**（C3）。
- 最后在你的 Mac 上实际升级一次（0.2.3 → 0.2.4，或者用环境变量指向一个测试用的候选版本）。

## 9. 需要同步修改的文档

- `README.md` 和 `README.zh-CN.md` 的升级说明：普通升级在 App 里点一下就行；第一次装、跨数据格式升级仍用 `install.sh`；辅助功能那句按 C3 的结果改。
- `docs/install.md` 和 `docs/install.zh-CN.md`：同上。
- `CHANGELOG.md` 和 `CHANGELOG.zh-CN.md`：新功能。
- `docs/compatibility.md`：第 5 节写明在 App 里安装的条件；第 6 节的发布检查清单加上 zip 必须叫 `GoldenPassport-<版本>.zip`、必须公证并装订票据。
- 菜单「每天自动检查更新」的说明：补一句「只有点了「下载并安装」才会下载」。

## 10. 留给实现者

- 类型和文件怎么命名，进度窗口怎么实现。
- 第 3 步能不能在 `.GoldenPassport.app.updating` 里直接运行（`Bundle.main` 是否能正确识别这个包）。如果不行，就改到第 5 步之后、第 6 步之前运行，失败时按第 6 步的方式恢复。
- 确认 `--migrate-data` 在 `already-migrated` 时不写任何文件，因为它是在旧版本还在运行时执行的。
- 确认 `notarized` 这个要求在离线时能靠装订的票据通过；不行就改用 `SecAssessment`。
- 第 4 步之前，「管理账号」等窗口里有未保存的输入时怎么处理：提示用户先关掉窗口，或者在弹窗里直接说明。
- 各个超时的具体数值、错误文案，以及新增字符串的英文翻译（`LocalizationTests` 会检查中英文是否对齐）。

## 11. 待确认的决定

这些是我拿的主意，请确认：

1. 只在点了「下载并安装」后才执行，不在后台静默安装。
2. `compat.json` 缺失或读不懂（兼容性不明）也算不允许，只给发布页面。
3. 旧版本移到废纸篓，不在 `~/GoldenPassport-backups` 里做备份（数据没动，也避免多一份明文）。
4. 信任整个 Team ID，而不是只认一张证书（第 6 节）。
5. 更新成功后，新版本弹一次「已更新到 …」。
6. 没有写入权限或位置不对时，不弹管理员密码框，退回发布页面并说明原因。
